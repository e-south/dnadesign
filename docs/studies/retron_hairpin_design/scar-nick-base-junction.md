## Scar-Nick Base-Junction Context

**Owner:** dnadesign-maintainers
**Last verified:** 2026-05-09

Use this page when the retron hairpin question is about the four-base stem base,
Type IIS scar choice, `scar_nick` terminal nick geometry, or profile-diverse
`S0=M` scar coverage. Use `routes.md` for the command ladder.

### Coordinate Convention

The study convention for basal profiles is:

```text
Match profile = S3 S2 S1 S0

S3 = L0:R3   retron-proximal
S2 = L1:R2
S1 = L2:R1
S0 = L3:R0   payload-proximal / ligation pair

M = Watson-Crick match
W = G:T / T:G wobble
X = hard mismatch
```

Current biological references:

```text
B26 = CGGG / ACAG = M X M X   works
B43 = CAAG / CTCG = M X M M   fails
```

For scar-compatible candidate designs, `S0` must be `M`. The exact B26 `MXMX`
profile remains useful as a cap/base control, but it is not scar-compatible
under that ligation constraint.

### Design Center

The `scar_nick` base-junction lane should be centered on feasible profile
coverage, not exact B26 sequence preservation. B26 and B43/172 are biological
calibration points:

```text
B26 tells us that a disrupted basal architecture can work.
B43/172 tells us that a more clamped scar-compatible architecture can fail.
```

They do not make exact B26 left/right sequence retention the design objective.
Under the exact terminal-nick policy, the useful question is:

```text
Within the `scar_nick`-feasible retained scar space, how do we cover the most
informative S3/S2/S1 architectures while keeping S0 matched and ligatable?
```

### Scar-Nick Processing Policy

Current processing policy:

```text
exact terminal nick
top or bottom nick allowed
zero protected bases downstream of the nick
downstream degenerate N only
S0 must be M for ligation
```

Do not use the one-protected-base relaxation as the next default. It did not
expand the current catalog solution space. A two-protected-base relaxation would
open additional bottom-strand families, but that is outside the current
preferred policy.

### Strict Retained Scar Families

`BbsI-HF` supports:

```text
AATG, AGTG,
CTCA, CTCC, CTCG, CTCT,
GTGA, GTGC, GTGG, GTGT
```

`PaqCI` adds:

```text
TTCA, TTCC, TTCG, TTCT
```

`BsaI-HFv2` currently has no strict catalog-backed retained scar under this
top-or-bottom terminal nick policy.

### Selection Principle

Top/bottom nick flexibility helps because the discarded strand can satisfy
enzyme-route constraints without defining the retained biological scar. The
current practical route is to select profile analogs by set coverage across
`S3/S2/S1`, not by literal B26 sequence distance:

1. Keep `S0=M` for ligation.
2. Treat `S3`, `S2`, and `S1` as controlled design variables.
3. Use `W` as a ligation-aware disruption class, especially when a middle
   position would otherwise become a hard mismatch.
4. Keep the active scar panel to at most two non-Watson-Crick positions total.
5. Allow up to two hard `X` positions only when one is the S3 edge-like
   disruption; `XXMM` and `XMXM` are active S3-edge double-hard buckets.
6. Keep `MXXM` out of the active panel because it puts hard `X` calls at both
   middle positions `S2/S1`. It can remain a reserve comparator, not a default
   hit.
7. When a hard mismatch is unavoidable, prefer lower T4 mismatch class tier
   before GC or reference-distance tie-breaks. `G:T/T:G` should be classified as
   `W`, not `X`; remaining hard mismatches should avoid tier-3 choices when a
   tier-2 alternative exists in the same profile bucket.
8. Prefer lower GC / more AT-rich examples only after profile, strand route,
   support/disruption, and hard-mismatch tier ties.
9. Track which strand is nicked and which strand survives, because the nicked
   strand can carry enzyme-recognition burden that is removed in the next step.

### Core Profile Panel

The compact `scar_nick` target panel should cover these scar-compatible profile
buckets:

| Target profile `S3 S2 S1 S0` | Role |
| --- | --- |
| `MXMM` | failure-like scar comparator |
| `WXMM` | S3 wobble candidate |
| `XWMM` | S3 hard plus S2 wobble architecture |
| `MWXM` | S2 wobble plus S1 hard architecture |
| `MXWM` | S2 hard plus S1 wobble architecture |
| `XMWM` | distributed S3 hard plus S1 wobble architecture |
| `WMMM` | S3 wobble-only comparator |
| `MWMM` | S2 wobble-only comparator |
| `MMWM` | S1 wobble-only comparator |
| `WWMM` | S3/S2 double-wobble comparator |
| `WMWM` | S3/S1 double-wobble comparator |
| `MWWM` | S2/S1 double-wobble comparator |
| `XXMM` | active S3/S2 double-hard bucket |
| `XMXM` | active S3/S1 double-hard bucket |

The first comparison is:

```text
MXMM -> WXMM -> XWMM
```

That isolates whether S3 softening or S3 hard disruption plus a middle wobble
can compensate for the forced `S0=M` ligation pair. The second comparison
separates `X+W` placement without allowing two hard mismatches:

```text
WXMM = S3 wobble + S2 hard
XWMM = S3 hard + S2 wobble
MXWM = S2 hard + S1 wobble
MWXM = S2 wobble + S1 hard
XMWM = S3 hard + S1 wobble
```

This excludes the middle-middle double-hard comparator `MXXM` from the active
panel while still allowing S3-containing double-hard buckets. The
W-only and W+W buckets are included after the core six buckets so extra capacity
goes to `G:T/T:G` alternatives rather than repeated hard-mismatch variants.

### Program Handoff

`scar_nick` runs should emit enough structure to select one candidate per
profile bucket and audit sequence capacity after the nick-disposal step:

```text
profile_s3s2s1s0
profile_payload_outward
S3_pair_identity
S2_pair_identity
S1_pair_identity
S0_pair_identity
M_count
W_count
X_count
non_watson_crick_count = W_count + X_count
middle_hard_count
middle_wobble_count
worst_hard_mismatch_tier
hard_mismatch_tier_sum
middle_hard_mismatch_tier_sum
edge_hard_mismatch_tier_sum
ligation_support = M_count + 0.5 * W_count
effective_disruption = X_count + 0.5 * W_count
GC_fraction
TNNA_flag
enzyme_route
nicked_strand
surviving_strand
retained_scar_source
discarded_strand_enzyme_burden
```

The explicit downstream handoff table is:

```text
export/table__scar_nick_candidate_pair_calls.csv
```

It is intentionally row-per-candidate-per-site, so downstream review does not
have to unpack nested JSON from the candidate table. Each row carries the
candidate rank, `left_base`, `right_base`, `site`, left/right nucleotide,
aligned right nucleotide, `class_label`, mismatch booleans, mismatch class,
T4 mismatch tier, profile, route, and strand fields.

Ranking should satisfy profile-bucket coverage first, then prefer ligation
support of at least two effective pairing units, no more than two
non-Watson-Crick positions total, no hard-hard topology across `S2/S1`, useful
S3 diversity, lower middle-hard and total-hard mismatch tier, and
non-redundant BbsI-HF/PaqCI route diversity.

### scar_nick Schema Contract

The `scar_nick` schema should keep these fields first-class so the executable
can support profile-bucket selection rather than hidden B26/B43-distance
heuristics:

```text
nicked_strand
surviving_strand
downstream_protected_nt_allowed = 0
downstream_must_be_degenerate = true
profile_order = S3_S2_S1_S0
s0_match_required = true
active_max_non_watson_crick_pairs = 2
active_max_hard_mismatches = 2
forbid_active_middle_middle_double_hard = true
prefer_lower_middle_hard_mismatch_tier = true
prefer_lower_hard_mismatch_tier = true
anchor_mode = exact_left | exact_right | profile_analog | surviving_strand
```

The checked-in BbsI-HF `scar_nick` spec now uses this S-order, S0-matched
profile-bucket objective. Treat broader enzyme-route claims, especially
PaqCI-specific route diversity, as catalog-run outputs to regenerate rather
than hand-assumed sequence tables.
